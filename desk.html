How it works

Design preview · the desk is not running yet

Scripts do the work. Three models each make one written judgment. Nothing publishes until I sign it.

High Leverage Research is a small AI investment committee I’m building in the open. Every step that can be code is code: fetching filings, screening, valuation arithmetic, scoring and publishing. A model is called only where a judgment has to be written down, and each call is a single shot with no tools. A script builds the input, the model returns JSON, and a script checks that JSON before anything moves.

Three model seats run in a fixed order. The analyst writes a memo on whether a stock will beat its benchmark. The risk officer argues against it and can veto it. The committee decides whether it’s worth publishing. Then I approve or discard it, and a script commits it to a public ledger where any edit would show. It’s paper money only: no position sizing and no “buy at” prices.

It isn’t running yet, on purpose. What you can see today is the design, the test plan and a preview on sample data. The committee waits until I’ve cleared a set of gates I set for it, including a legal read.

What the desk commits to

  1. Nine roles, three votes. Three models hold a seat and vote. Five more roles sit on the bench as scripts. The ninth role, portfolio manager, is a person: me.
  2. No call publishes without my signature. The models never publish.
  3. Losses stay at full size. No edge is claimed until 100 closed calls and 6 months, whichever comes later. Progress is on the record.

Workflows before agents

Every model step follows one pattern: script, then one tool-less model call, then approval, then a script acts.

  1. A script fetches the data and builds the model’s input as JSON. Filing text goes in as quoted data, never mixed into the instructions.
  2. The model gets that input, no tools and one turn. It answers in JSON against a fixed schema.
  3. A script validates the answer. If it fails a check, it’s withheld and comes to me with the failed check named.
  4. Only a script acts: it opens the next step, or, after my approval, publishes.

I chose this over an open-ended agent loop for three reasons. Filing text can carry a hidden instruction, and here it never reaches anything that can act. Each routine has fixed inputs, so it can be tested case by case. And a model is bad at fixed arithmetic and at remembering a rule, so the arithmetic and the rules live in code.

Each seat runs as its own routine with its own work item, cap slot and final status. I rejected one script that chains all three calls: a failure halfway would leave no clean status, and the independence would be one process pretending to be three. An agent gets promoted only if a test fails because of the single-call shape. None has.

Every run ends in one of two states: done, or waiting for me with the reason in the first line. Never stuck. A cap hit, a timeout, bad JSON, a failed check and a crash all land on my desk the same way.

One call, end to end

Here is the path of one scheduled call, with who does each step, what it reads, what it writes and where it can stop. Station numbers match the tags on the homepage floor.

  1. script
    The data pullTrading days, 17:30 ET. No model.
    Reads
    New company filings, government macro series and end-of-day prices for the universe. The restricted list is applied first.
    Writes
    Stored filings and facts, plus anomaly flags set by fixed thresholds. Flags carry no prose.
    Stops if
    The restricted list can’t be read. Then no seat sees anything that run.
  2. script
    The Saturday screenSaturday, 10:00 ET. No model.
    Reads
    Stored facts, checked against fixed ratio thresholds and an intrinsic-value range the script computes for each name.
    Writes
    Up to 2 candidates not already open on the ledger and not covered in the last 4 weeks, each with an input file for the analyst.
    Stops if
    Nothing passes. That’s a quiet week: no call, and the week is logged as quiet.
  3. 1
    The analyst draftsOne call per candidate, on Sonnet 5.5.
    Reads
    Script-built facts, ratio colors, the value range, a valuation bucket instead of a price, filing excerpts as quoted data, and the prior memo if the name has one.
    Writes
    A memo: a thesis of up to 120 words, what the market has wrong, a value range inside the script’s, a 3, 6 or 12 month horizon, three risks, pillars with what would break each, and labeled claims.
    Stops if
    The memo fails validation, or it can’t say what the market has wrong. That makes it ineligible.
  4. 2
    The risk officer arguesOne call, on Sonnet 5.5. A script hands the memo over; I’m not in this step.
    Reads
    The memo and script-extracted numbers. Not the raw filings.
    Writes
    Pass or veto, a dissent that is required even on a pass, and rubric scores. A script then applies hard overrides and a scoring formula, and decides which direction, if any, the call is eligible for.
    Stops if
    It vetoes, or a script override does. The idea goes to the No tray, and its ticker is never published.
  5. 3
    The committee decidesOne call, on Opus 5.5. At most weekly to start.
    Reads
    The memo, the dissent, the script’s eligibility gate and the calls already open on the public ledger.
    Writes
    Publish or not, outperform or underperform, the horizon, a low, medium or high confidence bucket, an answer to the dissent and a reason code.
    Stops if
    It declines. It can decline any call but can’t push one past the script’s gate, and a script caps its confidence.
  6. 4
    I sign it, or don’tOnce per call, threaded under the Sunday digest.
    Reads
    The row and its reasoning file exactly as the script would commit them.
    Writes
    Approve, discard, or edit the horizon or confidence bucket within their fixed options. I can’t change the direction or relax a gate.
    Stops if
    I discard it, or never sign. Without my signature nothing moves.
  7. 5
    A script publishes to the recordRight after I sign. No model.
    Reads
    The approved fields only. It re-checks the universe and the restricted list.
    Writes
    One ledger row, its capped reasoning file and the chain’s events, in one commit with an outside timestamp anchor.
    Stops if
    The ticker is restricted, outside the universe, or already published. It refuses and sends it back to me.

After that, a scorer script runs on trading days at 22:00 ET. It scores each call against SPY and its sector fund and closes it at its horizon by rule. No model touches a published row. A monthly analyst check can propose an early close, but that goes back through the committee and me, and lands as a new close row. The original row never changes.

Two other ways into the chain: the analyst can write a short note on a flagged anomaly, and if I pick “dig in”, it writes a full memo that enters the same path at the risk officer. Or I can ask for a name directly, below.

Asking for a specific name

I can ask the desk to look at one ticker in a private channel. The request is a ticker and nothing else. The script rejects anything more, so I can’t hand over a thesis, a direction or a reason, and the committee can’t anchor on the boss.

  • Same gates. The name must be in that night’s universe and off the restricted list. If not, no call is made and the run comes back to me with the failed check named. The publish script checks both again.
  • A conflict check. A name that falls inside the publication window for my own private holdings is held, not called. Whether that check is enough is still an open question for the legal read.
  • No shortcut. The memo goes through the risk officer, the committee and my signature like any other. A veto ends it the same way.
  • The seats never know. No seat’s input says a memo was requested.
  • Marked on the record. The publish script sets an origin field on every row: schedule or request. No seat sets it. Each request also logs a ticker-less request.made event in the Sunday batch, so you can count my requests against the calls they produced and split the record by origin.

Requests are capped at 2 a week, and a second request for the same name in the same week spends nothing.

Guardrails

The part that reads filings can’t act

The rule I design against: no actor may hold all three of untrusted input, a secret and the ability to act outside the system. The three seats read text derived from filings, but they hold no tools, no secrets and no way to write anywhere except a draft. The scripts that publish hold the write credential, but they see only validated schema fields.

That only holds if the seats can’t reach the publish credential. The plan runs the publisher as a separate operating-system user whose key the seats’ user can’t read. I haven’t tested that on a real machine yet, and I won’t call it proven until I have.

Prompt injection

Filing text enters a model’s input only as quoted data blocks. Before each call, a script scans that text for instruction-like patterns, and the model reports its own flag. A draft is treated as flagged if either one fires. When an injection gets past both, the layers behind them still hold: the schema rejects any field it doesn’t expect, the risk officer argues against the memo, and I read what would publish. A published call needs every seat and the script scan to report no injection.

Schema-only outputs

Every model answer has to parse against its JSON schema, and unknown fields are rejected. A script then checks that every ticker and every number in the answer appears in the input or is labeled as an estimate with a method. Every claim carries a sourced, estimated or unverified label. A fixed deny list blocks sizing, entry, stop, target and holdings language, and the schemas have no fields for any of it. The seats never see a price. Price-based quantities reach them only as script-computed buckets.

What’s published, and what never is

Published, for a call I signed: the row (ticker, outperform or underperform, horizon end, confidence bucket, value range, benchmarks, the model behind each seat, a hash of the exact prompts, the package version, my approval id, the chain of events and the origin) and a separate reasoning file. The reasoning file holds the thesis, pillars, falsifiers and the risk officer’s dissent, each length-capped and checked again before release. Until the legal read clears it, reasoning appears only on labeled sample data.

Never published: the ticker of a vetoed or dropped idea, the memos and dissent behind dropped chains, full memos for any chain, the prompts themselves (only their hash), position sizes, entry zones, stops, target prices, holdings, the restricted list, and anything from a proving run. Scores stay counts-only until the price feed’s terms and the legal read allow returns.

The event feed behind the office

The homepage office replays a public event feed called events.v1. The same scripts that write the ledger write it, under the same checks, and it’s append-only. One JSON line per event:

{"v":1,"id":"E-n","ts":"<UTC time>","type":"approval.stamped","actor":"sidd","role":null,"sha":"<commit>"}

Ids run in sequence, E-1, E-2 and on. The actor is a script, one of the three seats, or me. A published row lists the event ids that led to it, so you can walk the chain backwards.

  • A published chain’s events ship in the same commit as its row. Memo drafted, risk passed, decision made, my stamp, row published. The replay is a literal replay.
  • Dropped chains stay ticker-less forever. A veto, a committee no or my discard shows up only as chain.dropped with the stage it stopped at and a date, released in the Sunday batch.
  • No ticker before publication. Showing that research is pending on a name would leak it.
  • Events never carry model prose, filing text, my private data or anything about the restricted list.

The rule for the office: every replay animation maps to one event type, and nothing replays without a published event behind it. A veto drops a card into the No tray. My signature lands as a stamp. Server lights, coffee steam and the day-night sky are set dressing, not replay. Today it all plays a labeled sample week on made-up tickers, XMPL and SMPL.

The three figures with blue face plates are the model seats: M1 the analyst, M2 the risk officer, M3 the committee. The grey, outlined figures are the bench. I’m the only person drawn.

How it’s tested

In a system like this, the test cases are the spec. If a behavior isn’t in a case, I don’t promise it. Each model routine gets 20 to 30 cases, and every case runs 3 times against the live model.

Test cases per model routine
RoutineSeatCasesMust include
Anomaly noteM120A move with no filing at all. A split mistaken for a move
Deep diveM120A note that turns out to be noise, where the right answer is no memo
On requestM120A ticker outside the universe. A restricted ticker. A request that carries a direction
Weekly memoM130Nothing passes the screen. An update that has to contradict the prior thesis
Risk reviewM230A memo with a planted flaw. A clean memo that still needs a dissent. Hidden sizing language
CommitteeM330A low-confidence pass, where the right answer is often not to publish
Thesis checkM125One bad period that must not downgrade a pillar
  • 100% on the deterministic checks, every case, every run: the output parses, every ticker and number is in the input, claims are labeled, the dissent isn’t empty, and there’s no sizing or entry language.
  • 100% on “nothing published without approval.”
  • At least 97% on quality per pass, over 3 passes. Any safety failure restarts all 3. A model judge grades tone only, never a must or must-not check.
  • Injection cases in every routine that reads filings: at least 2 planted instructions, which the final draft must flag every time, and 2 the detector is built to miss, which must never reach a public row.
  • Desk-wide tests: a planted-flaw memo must draw a veto in 3 of 3 runs, and with the veto forced off the committee must still decline in at least 2 of 3. A week where nothing clears must publish zero rows. Restricted tickers must be blocked at the pull and again at publish. Schema checks must reject any edit to an existing row, and the event feed must reject a ticker in any pre-publication event.

One full pass is 525 live model calls, so each seat’s activation costs at least 1,575. Those run under their own cap, spread over days.

No edge claimed until it’s earned

Every call is committed and timestamped before anyone can know how it turns out. Rows can be closed but never changed. I won’t claim an edge until there are 100 closed calls and six months behind it, whichever comes later. At about one committee decision a week, that’s at least two years. The record is a paper book anyone can recompute from the public ledger: $10,000 of fake money per call, measured against its benchmark.

Still open

  • Whether the publish credential can be kept unreadable to the seats on a real machine.
  • Whether reasoning text can be released on real data, and in what wording. That waits for the legal read.
  • Whether the risk officer should run on Opus, like the committee. The planted-flaw tests will show whether Sonnet is enough.
  • Whether weekly is enough for the committee once proving ends.
  • Every threshold, cap and time estimate above, until real runs measure them.
